# Stage 2 implementation proposal

**Status:** implementation approved. `feat/stage-2-community` is the target branch. The Stage 1 baseline was brought forward from `main`, and its acceptance run is deferred. Keep the work items below as separate reviewable commits on the target branch.

## Change sequence

Each change includes the API and migration work it needs, the user-facing flow in Polish and English, and tests for the new behavior. Keep each change reviewable and exercise the last completed flow before starting its dependents.

| Order | Work item          | Change                                                                                                                                                                                                                    | Acceptance                                                                                                                                                                                                                                                               |

Keep the existing default of one use and 24 hours when creating a link through the Stage 1 flow. | Existing invitations and participant identities still work. Concurrent redemption respects the limit. Revoked or expired links stop new admissions. Switching modes preserves existing memberships.                                                                      |

## Implementation boundaries

- Go remains authoritative for community permissions and voice admission. Better Auth owns accounts and sessions. Preserve the existing browser origin checks and the Go-gated LiveKit signaling path when testing native clients.
- Evolve the shared `v1` HTTP and WebSocket contracts with each change. Keep Stage 1 identities, chat history, and invitations usable after schema updates. Verify migrations with existing test data and fresh PostgreSQL 19 volumes.
- The GPUI task is a prototype. Stage 4 delivers the full Windows and Linux client with one-to-one parity with the Electron UI. Preserve layout, colors, typography, icons, component states, keyboard behavior, and responsive behavior. Compare equivalent screens at matched window sizes and display scaling before accepting the port. macOS uses Electron for that release and has a separate Swift client planned for Stage 8. Global push-to-talk and package validation belong to Stage 4.
- Explain the limits of anonymous bans and lost guest credentials in the applicable screens. Custom roles, attachments, direct messages, screen sharing, and camera remain later work.

### Windows and Linux GPUI prototype

Use Rust and Cargo with [GPUI](https://gpui.rs/) for the native UI. The following crates are the proposed starting set. Pin the toolchain, crate versions and platform features after a build and audio call pass on each OS.

- **Networking and data:** Tokio for asynchronous network work, [reqwest](https://docs.rs/reqwest/latest/reqwest/) with rustls and cookie support for HTTPS, [tokio-tungstenite](https://docs.rs/tokio-tungstenite/latest/tokio_tungstenite/) for secure WebSocket events, and `serde` with `serde_json` for the API payloads.
- **Voice:** the official LiveKit Rust SDK, crate `livekit`, with [PlatformAudio](https://github.com/livekit/rust-sdks/blob/main/docs/ADM_PROXY_DESIGN.md) as the first option for microphone capture and speaker playback. Verify the SDK's signaling through Go and device support on both platforms before adding an audio dependency.
- **Credentials:** evaluate [`keyring`](https://docs.rs/keyring/latest/keyring/v1/index.html) with Windows Credential Manager and Linux Secret Service for credentials separated by server origin.
- **Rust checks:** `cargo fmt --check`, `cargo clippy` and `cargo test`. Record Windows and Linux build prerequisites and the tested Linux desktop session.
