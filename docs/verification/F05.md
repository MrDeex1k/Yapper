# F05 verification — 2026-09-28

Candidate 0.5.0, not a published release. Environment: OrbStack Docker 29.4.0, aarch64, 12 logical CPUs, 12,599,844,864 bytes allocated RAM; LiveKit v1.13.7. Two independent Chrome sessions on the same Mac used synthetic microphone/camera/capture sources. The screen source was also Chromium's generated test pattern, not a physical display, despite the picker-targeting flag. This validates transport and rendering, not real OS capture or acoustic quality.

## Exercised acceptance

- Admin uploaded a text attachment and sent it in chat; a member received the event, downloaded it, and the downloaded bytes matched the original.
- Member searched history and found the message; unread count advanced to zero with visible history.
- Both clients joined one voice room. Member decoded the admin camera (initial adaptive layer 320×180) and screen (640×360), separately and simultaneously.
- Pause incoming video removed the remote video element; resume restored decoded frames. This test found and fixed an SDK event-order issue that previously left a frozen frame.
- Sender stopped both publications and clients left the room.
- PostgreSQL integration/race tests cover attachment authorization and quotas, search isolation, edit/retry preservation, monotonic read state and media source policies.
- Upgrade test applies the actual 0.4 migrations, inserts an old-format message, applies the new migrations twice, and checks history plus idempotent retry. This is a schema upgrade test, not an upgrade between published container releases.
- PTT safety timeout retains the held-key latch until release, preventing auto-repeat reopening the microphone; physical keyboard acceptance remains pending.

## Separate local SFU measurements

Each scenario has two connected synthetic microphones in one room. Camera adds one publishing camera and one subscriber. Screen adds one screen publication and one subscriber, with camera off. Samples are not randomized, start from a warm SFU, and include media-control traffic. CPU is Docker's container percentage (100% means roughly one logical CPU), not percentage of the whole host. Memory is the sampled peak, not a guaranteed ceiling.

| Scenario | Samples | First-to-last interval | Mean CPU | Peak memory | Cumulative network RX / TX, first → last |
| --- | --- | --- | --- | --- | --- |
| voice | 7 | 18.34 s | 5.07% | 88.64 MiB | 3.27MB / 1.25MB → 3.76MB / 1.72MB |
| camera | 7 | 18.26 s | 6.13% | 104.10 MiB | 7.16MB / 3.22MB → 10.8MB / 5.61MB |
| screen | 7 | 18.29 s | 5.81% | 110.70 MiB | 32.7MB / 20.3MB → 34.6MB / 21.4MB |

Network counters are rounded container-lifetime totals; subtract first from last for an approximate interval delta. Raw samples: [voice](media-voice.json), [camera](media-camera.json), [screen](media-screen.json). Reproduce with two joined test clients and `python3 scripts/measure-media.py voice path-to-new-output.json` (or camera/screen). The command samples an explicitly selected local container and refuses to overwrite its output. These short local samples do not establish maximum capacity, production bandwidth or WAN quality.
